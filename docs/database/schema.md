# Persistence schema plan

## Scope and design goals

The recommended v2 rollout target is a **fresh, empty PostgreSQL database** using this normalized schema. The `0001` baseline creates legacy-compatible base tables so the following additive migrations also support an optional legacy import path. `import_batches` and `import_records` are recovery provenance, not runtime prerequisites. Legacy PostgreSQL/local JSON import is not required for release; no migration or application startup automatically imports, wipes, truncates, or resets an existing database. Existing Vercel data may remain untouched and unused. If an operator separately chooses legacy recovery, retain the original sources and follow [migration-plan.md](migration-plan.md).

Use PostgreSQL migrations (not `CREATE TABLE IF NOT EXISTS` as a migration mechanism), UUIDs for new externally referenced IDs, `timestamptz` for instants, and explicit foreign keys. Existing integer IDs may remain as primary keys during expansion; new keys can be added without forcing a risky primary-key rewrite. Keep historical names and match results as snapshots so renaming or deleting a player does not rewrite history.

## Identity, ownership, and authorization

### Users and sessions

- `users`: retain the existing table and `id`, `username`, `password_hash`, and `created_at`; add `username_key` (canonical username) and lifecycle timestamps as needed. Make `username_key` unique and non-empty. Store only a password hash from a suitable password hashing algorithm, never a password or login token.
- `user_sessions`: `id UUID PRIMARY KEY`, `user_id REFERENCES users ON DELETE CASCADE`, unique 32-byte `token_hash`, 32-byte `csrf_token_hash`, `created_at`, `expires_at`, nullable `revoked_at`, positive `version`, optional `pending_guest_owner_id`, and optional non-secret client metadata. Store only protected hashes of opaque bearer/CSRF tokens. Index active sessions by `(user_id, expires_at)` and enforce expiry/revocation in server-side validation.
- Rotate session credentials on login and privilege changes; revoke on logout, password change, or account disable. Do not treat a user ID, JWT payload supplied by a client, or a cookie's decoded contents as authorization without validating a server-signed token or server-side session record.

### Guest sessions and data owners

- `guest_sessions`: `id UUID PRIMARY KEY`, unique 32-byte `token_hash`, 32-byte `csrf_token_hash`, `created_at`, `expires_at`, nullable `revoked_at`/`claimed_at`, positive `version`, and optional non-secret client metadata. The raw random token is returned only in a `Secure` (in production), `HttpOnly`, appropriately `SameSite` cookie. Bind guest access to the matching active server-side row; use the cookie only as a credential to look up that row. Never accept a cookie's UUID/string as a guest ID, or let a request choose an owner by supplying an ID. Use CSRF defenses for cookie-authenticated mutations.
- `data_owners`: stable ownership boundary for user data. Columns: `id UUID PRIMARY KEY`, nullable `user_id REFERENCES users ON DELETE RESTRICT`, nullable `guest_session_id REFERENCES guest_sessions ON DELETE RESTRICT`, `created_at`, `merged_into_owner_id REFERENCES data_owners`, and a check requiring exactly one of `user_id` and `guest_session_id` for a live owner. Add unique partial indexes on each non-null principal column. A disabled/quarantined legacy owner may be represented separately and must not authenticate requests.
- Every user-owned or guest-owned domain row references `owner_id REFERENCES data_owners ON DELETE RESTRICT`. Resolve `owner_id` from the authenticated server-side principal, not request data. Apply owner predicates to reads, updates, and deletes; use row-level security only as an additional defense, not a replacement for application authorization.
- On guest claim, establish the user session first, lock both owners, and in one transaction move the guest's owned rows to the user's existing owner (or bind the guest owner to the user if no user owner exists), resolve uniqueness conflicts, record an audit event, mark the guest credential claimed/revoked, and commit. The guest token is never enough to select an arbitrary user's owner. A retry must be safe.

### Name identity and collision handling

Names are labels, not identifiers. Assign IDs independently; never merge players or teams solely because normalized names match. For uniqueness within an owner, retain `name` for display and store a full canonical `name_key`: Unicode NFKC normalization, Unicode case-folding, trim, and collapse all Unicode whitespace. Canonicalization must be versioned and identical for online/offline paths. Do not truncate the canonical value or use a digest alone as the unique key; a digest can be an index aid, not identity. Enforce non-empty keys and unique `(owner_id, name_key)` for active players and teams (partial unique indexes if soft-deleted rows remain). Resolve import/claim collisions explicitly by preserving both historical IDs and asking for rename/merge; never silently overwrite.

## Domain tables

Column lists below describe the intended model; exact names/types can follow established application conventions.

| Table | Principal columns and purpose |
| --- | --- |
| `players` | Keep a legacy-compatible integer `id`, `name`, aggregate stat fields, and `created_at`; add `owner_id`, versioned `name_key`, `updated_at`, optimistic `version`, optional `deleted_at`, and nullable import provenance. Fresh installs create these rows under an owner; any backfill/import is optional. Stats are legacy caches; v2 standings derive from normalized matches and do not overwrite unreconciled legacy counters. |
| `teams` | `id UUID`, `owner_id`, `name`, `name_key`, timestamps, optional `deleted_at`; named reusable team belonging to one owner. |
| `team_members` | `(team_id, player_id)` unique membership plus `position`, `created_at`; both references must belong to the same owner. Enforce same-owner membership in a transaction/trigger or through owner-bearing composite keys/FKs. Team composition is mutable here; tournament and match snapshots are immutable. |
| `tournaments` | Keep a legacy-compatible integer `id`; add `public_id UUID UNIQUE`, `owner_id`, `name`, `mode`, `status`, version/timestamps, and optional `import_batch_id`. Retain legacy `date` and `standings` only for optional compatibility/import; normalized matches/enrollments are the v2 source of truth. Do not derive authorization from mode or JSON content. |
| `tournament_enrollments` | `id UUID`, `tournament_id`, `owner_id`, nullable `player_id`, `player_name_snapshot`, `enrolled_at`, `withdrawn_at`, optional seed/metadata. Unique `(tournament_id, player_id)` for a non-null player; retain a snapshot for imported/deleted players. Check that the tournament, owner, and player references agree. |
| `tournament_schedule_events` | Persisted `bye`/`rest` events with tournament/owner, sequence, optional enrollment reference, and player-name snapshot. These are not matches and have no score, winner, timing, or standings credit. |
| `fixed_team_entries` | One fixed pair per tournament: `id UUID`, `tournament_id`, `owner_id`, `entry_number`, optional reusable `team_id`, `team_name_snapshot`, creation time. Unique `(tournament_id, entry_number)` and `(tournament_id, team_id)` where applicable. This freezes pairing for fixed-team mode without changing reusable team membership. |
| `fixed_team_entry_members` | `(fixed_team_entry_id, position)` with `position` constrained to the two defined slots, nullable `player_id`, `player_name_snapshot`, and optional `enrollment_id`. Unique player per entry; prevent a player appearing in multiple entries in one tournament. Keep names even if player references later become null. |
| `matches` | Keep a legacy-compatible integer `id`; add `public_id UUID UNIQUE`, stable API `external_id`, required `tournament_id`, `sequence_no`, `normalized_status`, validated `normalized_started_at`/`completed_at`, `winner_side`, optional `idempotency_key`, version/creation time, and provenance. Legacy `start_time`, `end_time`, and `teams` remain untouched as optional import/source fields; v2 API reads normalized instants/sides only. Remove duplicated per-match ownership after callers are migrated; ownership is inherited from and checked against the tournament. Unique `(tournament_id, sequence_no)` and `(tournament_id, idempotency_key)` when key is non-null. |
| `match_sides` | `(match_id, side_no)` with `side_no` constrained to 1 or 2, score, optional side label; score non-negative. A composite FK supports participant membership. A completed match must have exactly two sides and a valid winner (or explicit draw); validate in the completion transaction. |
| `match_players` | `(match_id, side_no, position)` references a side, with nullable `player_id`, optional `enrollment_id`, and required `player_name_snapshot`. Enforce at most one appearance per match and consistent tournament/enrollment/owner references. Snapshot is immutable; ID can become null if the live player is removed. |
| `idempotency_requests` | `owner_id`, operation/scope, client-generated random key, request hash, status, response/result reference, `created_at`, `completed_at`; unique `(owner_id, operation, key)`. Reuse with the same hash returns the stored result; reuse with a different hash is a conflict. Never trust a key as identity or authorization. Apply a retention policy that exceeds client retry windows. |
| `rate_limit_buckets` | `bucket_key_hash BYTEA PRIMARY KEY` (32-byte secret-keyed HMAC from application code), `request_count`, `window_started_at`, and `reset_at`. Never persist raw IP, username, cookie, session token, or bucket identity. Consume with one atomic upsert so Vercel instances share fixed-window limits; prune expired rows in bounded batches. |
| `audit_events` | Append-only `id UUID`, timestamp, actor type and nullable `user_id` / `guest_session_id` (validated principal), `owner_id`, action, entity type/id, request/correlation ID, and redacted JSONB details. No passwords, raw session/guest tokens, or secret cookie values. Restrict update/delete to maintenance roles. |
| `import_batches` | `id UUID`, source type (`legacy_postgres` or `local_json`), source identifier/file label, content hash, importer/schema version, status, timestamps, counts, and sanitized error summary. Avoid storing secrets or full sensitive payloads. |
| `import_records` | `id UUID`, `batch_id`, source namespace/entity/key, source hash, target entity/id, status, and warnings. Unique `(batch_id, source_namespace, source_entity, source_key)`; use a stable source namespace plus source key for cross-run idempotency where appropriate. Preserve mapping for re-runs and support reconciliation. |

`team_members`, enrollments, fixed entries, sides, and match players must not permit cross-owner or cross-tournament references. Prefer composite candidate keys and composite FKs (for example `(id, owner_id)` on players and `(id, owner_id)` on tournaments) where feasible; otherwise validate the relationship in a transaction and add deferred constraint triggers. Foreign keys should not rely on application-only checks for ownership integrity.

## Constraints, indexes, and transaction rules

- Use `NOT NULL`, checks, `UNIQUE`, and foreign keys for invariants: exactly one live owner principal; non-empty normalized names; non-negative counters/scores; valid side/slot numbers; valid timestamps; and one match sequence per tournament. Use `ON DELETE RESTRICT` for historical principals and `ON DELETE SET NULL` only on optional live-entity references whose snapshots preserve history. Cascade only within dependent rows that cannot stand alone (for example, match sides when an explicitly purged tournament is permitted); normal user deletion should be soft-delete/disable, not cascade away history.
- Index all foreign-key columns used for joins/deletes. Add `(owner_id, created_at DESC)` on players/teams, `(owner_id, date DESC)`/`(owner_id, created_at DESC)` on tournaments, `(tournament_id, sequence_no)` on matches, `(tournament_id, enrolled_at)` on enrollments, and `(match_id, side_no, position)` on match players. Use partial unique indexes for live-name uniqueness and non-null idempotency keys. Validate index plans against actual query patterns before adding speculative indexes.
- Index the rate-limit expiry timestamp to support bounded cleanup. Its consume operation is a single `INSERT .. ON CONFLICT DO UPDATE` statement using database statement time; the statement may run directly or inside the same transaction as the protected mutation.
- Create/complete a tournament atomically: claim the idempotency key; insert tournament and enrollment/team-entry snapshots; insert matches, sides, and player snapshots; derive standings/stats from inserted results; update cached player aggregates; append audit/provenance; store the idempotent result; commit. On any failure roll back all writes. Lock/update aggregate rows consistently, or recompute them from canonical match results to avoid lost increments.
- Complete a match atomically: verify owner and tournament state; compare-and-set expected status/version; insert/update both sides and participant snapshots; set result once; update cached aggregates if those are maintained; audit and save the idempotent result. Use optimistic versioning or row locks to prevent concurrent score submissions from double-counting.
- Guest claim/import writes use a transaction and stable lock order; uniqueness collisions are surfaced as conflicts. Use `SERIALIZABLE` only where needed; otherwise use explicit row locks, unique constraints, and retry handling for serialization/deadlock errors.
- The offline JSON adapter should implement the same conceptual owner boundaries, uniqueness rules, snapshots, and idempotency as far as a single-process file permits. It is not a trusted authority for server identities. File writes should use a temporary file plus atomic rename and a backup; concurrent multi-process writers are unsupported unless a separate locking strategy is added.

## Legacy compatibility (optional)

Legacy `players.user_id` / `guest_session_id`, tournament `date` / `standings`, match `start_time` / `end_time` / `teams`, and duplicate match ownership columns remain in the additive schema for optional recovery. The recommended fresh-database rollout does not read, import, or dual-write the old deployment database; it may remain unused. If legacy import/cutover is explicitly approved later, preserve source data, quarantine unverified guest rows, reconcile before switching reads, and remove compatibility fields only in a separately reviewed contract migration.

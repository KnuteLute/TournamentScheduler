# Tournament Scheduler API v1

`openapi.yaml` is the contract for the Vue client and backend JSON API at `/api/v1`. It complements the merged domain contract in `docs/domain/scheduling-and-standings.md` and PostgreSQL model in `docs/database/schema.md`. PostgreSQL is the durable source of truth. The backend validates ownership, IDs, roster relationships, scores, schedules, standings, and lifecycle transitions; no decision is trusted merely because the Vue UI sent it.

## Ownership, sessions, and guest transfer

- Every account/guest has a stable data-owner boundary. Every player, reusable team, tournament, enrollment/team-entry snapshot, match, and idempotency record is owner-scoped (a match inherits its owner through its tournament). Derive the owner only from the verified server-side session and owner record. Never accept `ownerId`, `accountId`, guest IDs, or session IDs from request bodies, query strings, or client-selected resource IDs.
- Apply owner predicates to every read, join, update, and delete. Verify that every player/team referenced by a request belongs to the caller's owner and that nested entities belong to the same tournament/owner. Reject unknown, malformed, duplicate, or foreign IDs; never create fallback participants from unknown IDs. A foreign-owned resource is indistinguishable from an absent resource (`404`). SQL constraints/composite relationships must reinforce—not replace—application authorization.
- These requirements apply to every HTTP entry point, including legacy Express/EJS form routes. The Vue/API boundary is not a security boundary: EJS routes must call the same owner-scoped validation/domain services or be removed/disabled; no legacy route may bypass these invariants.
- Use a high-entropy opaque session/guest capability in the `__Host-ts_session` cookie; persist only its protected hash and resolve it to an active server-side session and owner. Set `Secure`, `HttpOnly`, explicit `SameSite=Lax` or stricter, `Path=/`, no `Domain`, and bounded expiry. Rotate credentials at authentication/claim and revoke on logout/expiry. No client-readable JWT or submitted ID is an owner authority. Do not log raw credentials or session material.
- `POST /sessions` is the safe no-session bootstrap: no caller-selected owner, same-origin/Origin and Fetch Metadata checks, rate limits, and a fresh random guest credential. It is intentionally the only write endpoint without `Idempotency-Key`: storing/replaying a raw secret to make bootstrap idempotent would violate the opaque-secret rule. Call it only if no usable session cookie exists, and do not retry once its cookie has been received. `GET /session` returns the CSRF token and a session ETag with `Cache-Control: no-store`.
- Require a session-bound CSRF proof plus same-origin/Origin checks on cookie-authenticated state-changing requests, including registration, login, logout, guest claim, and all tournament/player/team/match operations. If registration/login has a pre-auth guest cookie, `X-CSRF-Token` from that guest session is mandatory and validated. Without any session cookie, these two endpoints are safe authentication bootstraps: require same-origin/Origin and Fetch Metadata checks, reject cross-site credentialed requests, and only issue a session after successful credentials. An invalid/present session cookie is not treated as the no-cookie case. Do not enable credentialed cross-origin API access by default.
- Registration/login with a valid guest session authenticate first and rotate the session. Transfer guest data atomically when there are no unique-name conflicts; otherwise leave a server-bound pending guest claim and let the authenticated owner resolve it through `POST /session/claim`. Canonical name equality never merges identities or silently retains one record. Claim requires explicit new names for conflicting guest players/teams, preserves their stable IDs and historical snapshots, and moves all guest-owned rows transactionally. A failed claim moves nothing; revoke/mark the old guest capability claimed after success. Collision resolution must match PostgreSQL: Unicode NFKC, Unicode case-fold, trim, collapse Unicode whitespace; keep the full canonical `name_key` and enforce unique `(owner_id, name_key)` for active players/teams. Never use a digest alone as identity. Explicit merges, if ever supported, need a separate approved operation.
- Logout revokes the active session but does not delete owner data. Guest expiry/retention is a server policy and must not silently affect account data.

## Modes, roster, and schedule

Supported wire mode values are exactly `1v1`, `2v2_fixed`, and `2v2_rotating`. Fixed 2v2 is supported by the backend but is not offered in the mode-selection HTML; the UI presents rotating 2v2 first.

| Mode | Draft input and start validation | Schedule / team view |
| --- | --- | --- |
| `1v1` | At least two distinct owned player IDs; duplicate IDs and duplicate display names are rejected. | Every unordered pair exactly once in a round robin; odd rosters have explicit player byes. Team standings are single-player sides. |
| `2v2_fixed` | At least four distinct players, supplied as reusable team IDs. Teams must form a disjoint partition of the selected roster; no player is omitted or assigned twice. | Every unordered pair of fixed teams exactly once; odd team counts have explicit team byes. Team standings represent fixed teams. |
| `2v2_rotating` | At least four distinct owned player IDs. | Open-ended live slots of four distinct unpaused players; other eligible players rest. Partnerships are unordered ID pairs for team standings. No match is generated with fewer than four eligible players. |

Creation makes a `draft`; start validates and snapshots the complete roster, name labels, mode, seed, generator version, and schedule atomically before entering `active`. The seed and generator version are persisted and deterministic: identical canonical inputs/history/pause state produce the same IDs/order/assignments. Persist generated matches once; previews/navigation read persisted records and must not invoke unseeded randomness. A valid start must not replace another tournament on invalid input. Roster names and match-player labels are historical snapshots; later renames/deletion do not rewrite history. A player/team referenced by a draft/active tournament cannot be deleted while referenced.

`GET /tournaments/{id}/schedule` includes actual matches plus explicit bye/rest events. A bye/rest is not a match, has no score/winner/timing, and gives no standings or rotating-fairness credit. Rotating selection follows the merged domain fairness order: fewest accepted appearances, longest waiting, fewest consecutive appearances, partnership novelty when feasible, then persisted seeded tie-break. Skipped/void matches do not affect fairness history. Pausing a player excludes them from future generation but never rewrites an already-generated match.

## Lifecycle and timing

Tournament states: `draft -> active -> completed`, `active <-> paused`, and `active|paused -> cancelled`. Completed and cancelled are terminal. Finish is permitted early; it preserves completed results and schedule/status history and does not invent results for pending matches. Cancel is an explicit terminal transition and awards nothing for unplayed matches. Drafts may be edited/deleted; active/paused tournament mode and roster snapshots are immutable.

Match states: `scheduled -> in_progress -> completed`, `in_progress -> paused -> in_progress`, and an explicit unplayed `skipped`/void terminal state. Only one match may be in progress at a time without multi-court support. `POST .../start` sets `startTime` when actual play begins, never on schedule generation. A pause opens a pause interval; resume closes it. A completed match has two non-negative integer scores and exactly one `endTime`; skipped matches have no result and are not represented as 0–0. Score correction is an explicit replacement allowed only while the tournament is active; recalculate both tournament and owner-overall standings instead of counting a second result. Finish is idempotent.

Tournament pause blocks match changes while paused and preserves individual match state; resuming the tournament does not implicitly resume a separately paused match. Match pause/resume are explicit operations. If a player is paused while in the current in-progress match, that match changes to `paused` with an open participant-unavailable interval; unpausing the player does not auto-resume play. A scheduled match containing a paused player cannot start until resumed or explicitly skipped. Player availability changes alone never skip, score, or complete a match. If fewer than four unpaused players are available for rotating 2v2, remain active/waiting without fabricating a match or bye opponent.

## Standings contract

Standings are read models calculated only from completed, non-void matches. Scheduled, in-progress, paused, skipped, and bye/rest events contribute no played games or statistics. A completed 0–0 result is a draw. Credit each side/player once: wins, draws, losses, points-for, points-against, and `pointDifferential = pointsFor - pointsAgainst`. There is **no** soccer-style 3/1 `points` total and no unexplained points field.

- `GET /tournaments/{id}/standings?view=players` includes every roster player, including players with zero appearances.
- `GET /tournaments/{id}/standings?view=teams` is an independent projection: single-player sides in 1v1, every fixed team in fixed 2v2 (including zero-appearance teams), and only pairs with a completed appearance in rotating 2v2.
- `GET /standings?view=players` is the owner-scoped career/overall leaderboard over that account's or guest's completed match history, not the current process or whichever tournament happens to be active. It preserves the existing overall player leaderboard behavior while being correctly isolated by owner.
- `GET /standings?view=teams` is likewise owner/history scoped. Persistent fixed-team rows use stable team identity; rotating partnerships use the canonical unordered player-ID pair and are labeled partnership aggregates, not permanent reusable teams. In 1v1, team rows are single-player sides.

For both views rank by **wins descending, point differential descending, points-for descending**. Rows equal on all three values share a competitive rank (competition ranking); normalized name then stable ID determines display order only and MUST NOT break the rank. Do not add head-to-head, draws, or any unstated tiebreaker. Tournament tables are separate from overall career tables; neither is derived by sorting the other. The response exposes `wins`, `draws`, `losses`, `pointsFor`, `pointsAgainst`, `pointDifferential`, and `matchesPlayed`, not a `points` ranking total.

## Validation and error responses

- Accept JSON request bodies (and `application/merge-patch+json` for PATCH). Reject malformed JSON with `400`; return `422` for valid JSON that violates field/domain constraints. Reject unknown write fields. Validate types, lengths, mode allowlists, bounded roster sizes, score integer/range, canonical names, owner membership, disjoint teams, timing, and state transitions before mutation.
- Return RFC 9457 `application/problem+json`. Validation problems have `errors[]` with JSON Pointer, stable machine `code`, and safe message. Never return SQL, stack traces, secret/session values, or foreign-owner details. Include a trace ID for correlation.
- `401` means missing/expired/invalid session or credentials; `403` means failed CSRF/origin check; `404` includes absent and foreign-owned resources; `409` means state, uniqueness, or idempotency conflict; `412` means stale `If-Match`; `428` means required `If-Match` omitted; `429` may include `Retry-After`.
- Passwords are accepted only over HTTPS, never returned/logged, and stored using a contemporary password-hashing function. Login failures must not reveal account existence; rate-limit authentication and bounded expensive/write operations.

## Optimistic concurrency and idempotency

- Return strong ETags for mutable domain resources and the current session. Require `If-Match` on mutations of existing players/teams/tournaments, tournament and match lifecycle commands, match results, availability changes, and pending guest claim (claim uses the `/session` ETag). A missing required precondition returns `428`; stale ETag returns `412`. **Create operations** (`POST /players`, `/teams`, `/tournaments`) do not use `If-Match`. Session creation, login, registration, and logout are credential/session operations and do not use `If-Match`.
- Every state-changing operation except the explicitly documented `POST /sessions` bootstrap requires `Idempotency-Key`: creates, updates/deletes, auth transitions, session revocation/claim, and tournament/match commands. Scope records to owner + operation/route + key; store request hash and non-secret logical outcome transactionally. Same key/same request does not repeat the underlying mutation; same key/different request returns `409`. Authenticated retries may rotate and issue a fresh session cookie, but the original raw cookie/secret is never persisted or replayed. Anchor registration idempotency to the newly established owner and login/claim idempotency to the verified owner. Keys are not identity or authorization. Retain longer than normal retry windows. Session bootstrap is deliberately excluded because replaying a raw newly issued secret would require retaining it; clients must call it only when no usable cookie exists.
- Idempotency handles network retries; `If-Match` handles competing edits. Increment tournament version for every accepted mutation of its state/matches. Match mutations compare against the current tournament ETag and commit the state transition, result, schedule/fairness updates, derived standings, and audit data atomically using PostgreSQL transactions, constraints, and suitable row locks/conditional updates.

## Conventions and contract checks

- Pagination uses opaque `cursor`, `limit` (1–100), and `nextCursor`. IDs are opaque and are not authorization tokens. Timestamps are ISO 8601 instants; match timing uses `startTime`, `endTime`, and pause intervals.
- Do not expose persistence internals, owner IDs, raw sessions, or client-writable standings. PostgreSQL composite ownership relationships/foreign keys should reinforce the same-owner and same-tournament validations.
- Keep runtime request/response validation and Vue-generated types aligned to this OpenAPI contract. Breaking wire changes require a new API version. This v1 contract does not assume that legacy EJS routes are inaccessible or safe; all server routes must share the same domain/authorization rules.

Validate with an OpenAPI 3.1-capable validator before implementation and in API-contract CI, for example:

```sh
npx --yes @redocly/cli lint docs/api/openapi.yaml
```

Also check unresolved references, unique operation IDs, request/response examples, and parity between server runtime validation and published schemas. Application routes and database migrations are outside this planning-doc change.

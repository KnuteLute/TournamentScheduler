# Security threat model — Tournament Scheduler

**Status:** Planning baseline, before security remediation/implementation.
**Scope:** The Express/EJS application in `web/src`, its PostgreSQL and local-file persistence paths, browser cookies, and Vercel deployment configuration.
**Data sensitivity:** Low-to-moderate personal data (usernames, password hashes, guest/user player names, scores and tournament history). Integrity and ownership of these records matter even where confidentiality impact is limited.

## Review boundary

This document records risks to address while planning implementation. It is not a completed security code review, penetration test, or assurance that the observations are exhaustive. No remediation or security test results are asserted. The implementation and deployment must be reviewed and retested against the acceptance criteria before release.

## System and trust boundaries

- **Browser / untrusted client:** Sends account credentials, cookies, player identifiers, tournament mode, scores and pause/action fields. All request bodies, URL parameters, and cookies are attacker-controlled inputs, even when generated by the UI.
- **Express application:** Auth middleware reads a JWT cookie and a guest-session cookie. Routes read/write player and history records and modify tournament state.
- **PostgreSQL:** Stores users and records with `user_id` or `guest_session_id` ownership columns; SQL values currently appear to be passed as query parameters in the inspected database layer.
- **Offline database:** Optional JSON file persistence, with different concurrency and deployment characteristics from PostgreSQL.
- **Hosting / proxy:** Vercel or another TLS-terminating deployment controls environment secrets, HTTPS, request limits, and potentially response headers.

### Security-relevant assets

1. JWT signing secret and authenticated account sessions.
2. User and guest player lists, scores, standings, match and tournament history.
3. Integrity of player statistics and tournament results.
4. Account passwords and password hashes.
5. Availability of the web process and persistence store.

### Adversaries and failure cases

- Anonymous remote user able to submit arbitrary HTTP requests and cookies.
- Authenticated user attempting to read or alter another user's data.
- Cross-site page causing a victim's browser to submit state-changing requests.
- Attacker exploiting weak deployment configuration, shared process state, or unbounded input to impact other sessions or availability.
- Accidental environment misconfiguration, concurrent serverless requests/instances, or partial persistence failures.

Assume the database and TLS implementation are not already compromised. No trust should be placed in the UI, cookie contents, player IDs, or in-memory process locality.

## Preliminary risk register

Severity terms follow the rubric in `review.md`. These are planning risks inferred from the current application shape, not validated or closed findings.

| ID | Preliminary risk | Initial severity | Main security properties |
|---|---|---:|---|
| T-01 | A built-in fallback JWT secret allows token signing to depend on a public constant when deployment configuration is absent. | Critical | Authentication, confidentiality, integrity |
| T-02 | The guest-session cookie is a client-supplied ownership identifier, not a server-verified credential. A caller can choose/replace it; `HttpOnly` does not prevent request-level cookie spoofing. | High | Guest data confidentiality/integrity, account merge |
| T-03 | Tournament state is module-global, rather than keyed to an authenticated account or guest session. Requests from concurrent users/instances can share or overwrite the active tournament, and an unrelated session can view or finish it. | High | Isolation, integrity, confidentiality |
| T-04 | Tournament start accepts submitted IDs that do not resolve within the caller's player list by creating fallback participants. Tournament stats updates use participant IDs without an ownership predicate, creating a path to cross-owner stats changes. | High | Authorization, integrity |
| T-05 | Login/signup, score, mode, participant, pause, and action inputs lack consistent server-side type, range, size, and allowlist validation. Malformed or extreme inputs can corrupt results, trigger errors, or consume resources. | High | Integrity, availability |
| T-06 | Guest-to-account merge transfers records by the supplied guest cookie. Player-name collisions, concurrent merges, and non-unique ownership/name constraints have no explicit conflict policy. | High | Ownership, integrity, privacy |
| T-07 | Browser cookies are used for authentication and state-changing routes lack an explicit CSRF defense. Some state-changing navigation is also exposed through GET routes. | High | Integrity, account security |
| T-08 | No application rate limits are evident for login/signup or other expensive/write endpoints. | High | Availability, account security |
| T-09 | Security response headers/CSP are not configured in the app/deployment files inspected; templates use inline script/style, which needs a deliberate CSP plan. | Medium | Browser isolation, XSS impact reduction |
| T-10 | Error paths log database errors and exceptions; future logging or request tracing could expose credentials, cookies, tokens, SQL details, or personal data if not redacted. | Medium | Confidentiality |
| T-11 | SQL uses parameter placeholders in the observed dynamic-value queries, which is a positive control; preserve it and validate all data. The local JSON store still needs filesystem permissions, atomicity and concurrency controls. | Medium | Injection, integrity, availability |
| T-12 | Account names and player names have inconsistent normalization/validation across route and storage paths. Account uniqueness may be case-sensitive, and merge can create duplicate player names. Password minimum length is weak for account protection. | Medium | Account integrity, usability |
| T-13 | Cookie attributes are incomplete/implicit (notably SameSite), and secure-cookie behavior depends on `NODE_ENV`; deployment/proxy configuration must be verified. | Medium | Session security |

## Required design decisions

1. **Authentication secret and session lifecycle:** Fail closed at startup unless a high-entropy secret is provisioned; document rotation and revocation behavior. Keep only the minimum identity claims, verify expected algorithm/issuer/audience as appropriate, and set cookie `HttpOnly`, `Secure` under HTTPS, explicit `SameSite`, `Path`, and expiry. Define logout/session invalidation semantics.
2. **Guest identity:** Treat guest access as a capability, not a public database key. Use a server-generated, high-entropy opaque token, store only a protected representation where practical, validate its format, and never permit arbitrary client-selected guest IDs. Rotate the guest capability on account transition and define retention/recovery behavior.
3. **Per-session tournament ownership:** Store active tournament state in durable/session-scoped storage with an explicit owner and authorization check on every read/write. Do not rely on module globals or instance affinity. Ensure tournament records and derived updates remain scoped to the same owner.
4. **Authorization by lookup, not submitted identity:** Resolve every submitted player ID against the caller's owned player set; reject unknown, duplicate, malformed, or foreign IDs. Apply ownership predicates to every write, including aggregate-stat updates, and enforce relevant foreign keys/constraints.
5. **Account merge policy:** Permit a merge only from a validated pre-auth guest capability, use one database transaction, rotate/revoke that capability, and define collision handling (including same normalized player names and historical references). Prevent merges from affecting records owned by another user.
6. **CSRF and HTTP semantics:** Add CSRF tokens or an equivalently reviewed defense on all cookie-authenticated state-changing requests. Set explicit SameSite policy and validate Origin/Referer where appropriate as defense in depth. Convert state-changing GETs to POST; GET must remain read-only.
7. **Validation and limits:** Validate content type, field types, required values, lengths, Unicode/name normalization, allowed modes/actions, bounded participant counts, integer scores with documented bounds, pause IDs, and request body size. Reject invalid requests with safe client errors before state mutation.
8. **Abuse controls:** Rate-limit authentication attempts by suitable account and network signals, and bound write/compute endpoints. Return generic login failures and avoid account enumeration. Ensure proxy/IP trust settings cannot be client-forged.
9. **Browser and transport controls:** Add and verify security headers (at least content-type sniffing protection, frame embedding protection, referrer policy, and a CSP compatible with the templates); deploy HSTS only when HTTPS is guaranteed. Prefer nonces/hashes or remove inline script/style rather than weakening CSP without review.
10. **Data, SQL, and logs:** Preserve parameterized SQL for values, use transactions and scoped predicates, and test that no raw input is interpolated into SQL. Keep passwords/tokens/cookies out of logs; sanitize untrusted log fields, avoid returning internal errors, and set restrictive permissions/atomic writes if offline persistence is supported.

## Security invariants

- A request can access or mutate only records owned by its authenticated user or its validated guest capability.
- No client-supplied identifier alone establishes ownership.
- Every tournament operation is isolated to one owner and remains consistent across concurrent requests and server instances.
- Invalid input cannot create a participant, alter a score, advance/finish a tournament, or update another owner's statistics.
- Authentication fails closed when secrets or required security configuration are absent.
- State-changing browser requests are protected against cross-site request forgery.
- Logs and error responses contain no credentials, session material, or unnecessary personal data.

## Retest scope

Before release, run the functional and security test cases in `review.md` against both PostgreSQL and supported offline mode, test the deployed HTTPS/proxy configuration, and perform a fresh security review of the remediation diff. Release-blocking requirements in that document must all pass; unresolved critical/high risks require a documented exception approved by the security owner and product owner, not silent acceptance.
